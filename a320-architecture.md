## 1. Архитектурное резюме

### 1.1 Суть проекта

A320 Academy — русскоязычная образовательная платформа для виртуальных пилотов,
ведущая от нуля до уверенного самостоятельного пилотирования Airbus A320neo
(FlyByWire A32NX) в MSFS 2024, включая радиосвязь на VATSIM.

**[ФАКТ]** Ключевые ограничения и ценности проекта (из AGENTS.md, AVIATION_STANDARDS.md,
TECHNICAL_SPEC.md):

- Образовательный проект, НЕ официальная лётная подготовка.
- Русские объяснения + английская авиационная терминология.
- Обязательная маркировка: REAL AIRBUS / FLYBYWIRE A32NX / MSFS 2024 / SIMPLIFIED.
- Никаких выдуманных процедур, обязательные источники.
- Разработка на Android (Termux + Ubuntu 24.04 proot, aarch64) — сложная
  инфраструктура нежелательна.
- Контролируемые зависимости, отсутствие auth/облака до определения требований.

### 1.2 Главные архитектурные решения (кратко)

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | Монолит Flask + Application Factory, blueprint-модули | Минимальная инфраструктура для Termux, простое развёртывание |
| 2 | Контент — файлы (Markdown + YAML front matter) в Git | Версионирование, рецензирование, ноль БД-миграций для контента |
| 3 | SQLite — только прогресс пользователя, тесты, состояния | Встроенная, транзакционная, идеальна для локального приложения |
| 4 | Jinja2 + CSS custom properties, vanilla JS без фреймворка | Уже используется; интерактивность урока ограничена и предсказуема |
| 5 | Прогресс: localStorage сначала, SQLite серверно позже | Не требует auth на старте, миграция в БД спроектирована заранее |
| 6 | Система авиационной достоверности как данные, а не как догма | Схема source-tagging в front matter + CI-проверка + статус ревью |
| 7 | Практика: декларативные описания сценариев + SimVar-подобные состояния | Расширяемо на другие самолёты без переписывания движка |
| 8 | Модульность по самолётам: `content/aircraft/<id>/` | A32NX — первый «плагин» общей платформы |

### 1.3 Принципы

1. **Контент как код** — учебные материалы живут в Git, проходят review, версионируются.
2. **Данные важнее шаблонов** — урок это структурированный документ, а не HTML-страница.
3. **Достоверность встроена в схему** — нельзя опубликовать урок без источников и маркировки.
4. **Мобильный-first** — основной сценарий использования подтверждён средой разработки.
5. **Никакой магии** — никаких микросервисов, Docker, Kubernetes, сборщиков Node.

### 3.2 Почему монолит [ПРЕДЛОЖЕНИЕ]

- **[ФАКТ]** Разработка на aarch64 proot: ни Docker, ни очередей сообщений,
  ни нескольких процессов — нет смысла.
- Все подсистемы (контент, квизы, прогресс) тесно связаны общими моделями.
- Трафик — один пользователь локально; масштабирование по нагрузке не требуется.
- **[АЛЬТЕРНАТИВА: микросервисы]** Отклонено: операционная сложность несоизмерима
  с задачей; деплой и отладка на Termux стали бы невозможными.
- **[АЛЬТЕРНАТИВА: FastAPI/Django]** FastAPI — асинхронность не нужна, SSR удобнее
  в Flask, миграция дала бы мало. Django — тяжеловат (ORM, admin, миграции) для
  файлового контента; Flask уже работает и изучен. Оставляем Flask 3.1.3.

### 3.3 Application Factory и Blueprints [ПРЕДЛОЖЕНИЕ]

`app.py` превращается в пакет `academy/` с `create_app()`:

- Factory позволяет тестам создавать приложение с тестовой конфигурацией
  (временная БД, тестовый контент).
- Blueprints дают изоляцию доменов: `/courses`, `/practice`, `/quiz`, `/api`.
- **Обязательство [ФАКТ, AGENTS.md правило 2]:** существующие маршруты
  `/`, `/flight-training`, `/lesson/cold-and-dark` сохраняются дословно
  (перенос в blueprint `core`/`courses` с теми же URL-правилами).

### 4.2 Ключевые решения по структуре

- **content/ отдельно от app/** [ПРЕДЛОЖЕНИЕ]: контент — данные, а не код.
  Это позволяет валидировать, рецензировать и переиспользовать его независимо
  (например, экспорт в статический сайт в будущем).
- **aircraft/ отдельно** [ПРЕДЛОЖЕНИЕ]: профили самолётов — данные, на которые
  ссылаются курсы. Новые самолёты = новый каталог, а не правка ядра.
- **data/ остаётся** [ФАКТ]: каталог уже существует в проекте; SQLite-файл
  появится там по плану миграции, не раньше.

## 5. Модель данных

### 5.1 Разделение хранилищ

| Хранилище | Что содержит | Почему |
|-----------|--------------|--------|
| Git (файлы) | Контент, вопросы, сценарии, источники, профили самолётов | Версионирование, diff-ревью, рецензирование, оффлайн |
| SQLite | Прогресс, попытки тестов, состояние сценариев, заметки пользователя | Персональные динамические данные, транзакции |
| localStorage | Черновик прогресса до появления БД; кэш UI | Ноль инфраструктуры на старте |

### 5.2 Файловая модель контента (иерархия)

```
Course (course.yaml)
 └─ Module (module.yaml)
     └─ Lesson (lesson.yaml + sections/*.md)
         ├─ Section (markdown-файл, типизированный)
         │   ├─ Learning Material (блоки внутри section.md)
         │   ├─ Exercise (ссылка/inline-виджет)
         │   └─ Assessment (ссылка на quiz_id)
         ├─ Practical Task (ссылка на scenario_id)
         ├─ Mastery Criteria (в lesson.yaml)
         └─ Sources (в lesson.yaml, ссылки на sources.yaml)
```

## 6. Система учебного контента

### 6.1 ContentLoader и CourseRegistry [ПРЕДЛОЖЕНИЕ]

- При старте `create_app()` сканирует `content/courses/`, валидирует YAML
  и строит индекс (реестр) в памяти.
- Кэш с инвалидацией по mtime — чтобы в debug-режиме правки подхватывались без рестарта.
- Невалидный файл контента → **ошибка при валидации, а не при рендере**:
  сломанный урок не должен ронять всё приложение; курсы со статусом ошибки
  помечаются и скрываются из навигации (жёсткий режим — опция конфигурации).
- `tools/validate_content.py` — тот же валидатор как CLI: запускается перед
  коммитом и в тестах.

### 6.2 Типы уроков [ПРЕДЛОЖЕНИЕ]

| Тип | Назначение | Шаблон | Особый интерактив |
|-----|-----------|--------|-------------------|
| theory | Теория (аэродинамика, метео) | lesson/theory.html | схемы, слайды-сравнения |
| procedure | Пошаговые процедуры (Cold & Dark, запуск) | lesson/procedure.html | чек-лист с чекбоксами |
| system | Описание системы A320 | lesson/system.html | интерактивная схема/панель |
| scenario | Практический сценарий | lesson/scenario.html | пошаговый исполнитель |
| glossary | Терминология EN/RU | lesson/glossary.html | карточки, самопроверка |
| reference | Справочник (лимиты, таблицы) | lesson/reference.html | поиск по таблице |
| assessment | Итоговый контроль курса | quiz/quiz_page.html | тест |

Текущий `cold_and_dark.html` соответствует типу **procedure** — его содержимое
становится первым экземпляром схемы, а не уникальной страницей.

### 6.3 Блоки Learning Material [ПРЕДЛОЖЕНИЕ]

Markdown-расширения (кастомные, простые):
- `{{callout|warn|текст}}` — предупреждение/примечание (аналог `.lesson-note`).
- `{{source:FCTM-A32NX}}` — инлайн-ссылка на источник с тултипом версии.
- `{{certainty:real-airbus}}...{{/certainty}}` — блок с обязательной визуальной
  маркировкой (см. §8).
- `{{quiz:q-cold-dark-01}}` — встраивание квиза.
- `{{term:Cold & Dark}}` — ссылка на глоссарий с русским пояснением.
- `{{img:schematic|alt=...}}` — изображение с обязательным alt (доступность).

### 6.4 Терминология [ПРЕДЛОЖЕНИЕ]

- Единый `content/glossary/terms.yaml`: term_en, term_ru, abbreviation, definition,
  context, source.
- В шаблонах — автоподсветка английских терминов с подписью на русском.
- Русский текст объясняет, английский термин — рабочая лексика пилота
  (соответствует [ФАКТ] требованиям проекта).

## 7. Архитектура интерактивного обучения

### 7.1 QuizEngine и банк вопросов [ПРЕДЛОЖЕНИЕ]

- Банк — YAML-файлы, индексируется по course/lesson/topic_tags/difficulty.
- Типы вопросов: single, multiple, true-false, ordering (порядок действий
  чек-листа), matching (термин↔определение), fill-in, hot-spot (клик по зоне
  панели — для ECAM/панелей).
- Проверка **серверная** (POST /api/quiz/<id>/check): клиент не знает ответов —
  ответы в YAML не утекают в HTML.
- Результат → попытка в БД + обновление topic_mastery.
- **[АЛЬТЕРНАТИВА: клиентская проверка]** Отклонена для реальных тестов
  (утечка ответов), но допустима для несерьёзных self-check карточек.

### 7.2 Прогресс и интервальное повторение [ПРЕДЛОЖЕНИЕ]

- **Этап M2 (localStorage):** чек-листы и статусы уроков — JSON в localStorage
  по ключу `a320academy.progress.v1`. Ноль серверной логики, работает уже сейчас.
- **Этап M3 (SQLite):** `/api/progress/sync` переносит localStorage → БД при
  первом запуске (миграция без auth: локальный пользователь по умолчанию).
- **Повторение:** по topic_tags ведётся EWMA-оценка mastery; слабые темы
  поднимаются на главной («К повторению: …») и в генераторе мини-квизов
  (упрощённый SRS — интервалы фикс. схемы, без зависимости от внешних библиотек).
- **[АЛЬТЕРНАТИВА: полноценный FSRS/SM-2 сразу]** Отложено: для одного ученика
  простая EWMA-схема даёт 80% ценности; алгоритм SRS можно заменить позже,
  т.к. topic_mastery — данные, а не логика.

### 7.3 Практические сценарии и симуляция систем [ПРЕДЛОЖЕНИЕ]

Двухуровневая модель:

1. **Сценарий-сопровождение (M4):** пошаговый исполнитель на странице урока —
   «шаг → что сделать → что проверить → самопроверка ученика». Работает рядом
   с MSFS, состояние вводит ученик (чекбоксы/подтверждения). Реализуется
   ScenarioEngine на данных scenario.yaml. Не требует связи с симулятором.

2. **Симуляция систем в браузере (M5+, опционально):** интерактивные панели
   (оверхед, ECAM) как декларативные модели: `aircraft/systems/*.yaml`
   описывают элементы (switches, indicators) и правила переходов
   (`if elec.apu.master=on and elec.bat1=on then elec.apu.avail after 45s`).
   JS-рендер панели + серверные правила или предвычисленные таблицы состояний.
   Начать с **электроснабжения** (самая наглядная цепочка Cold & Dark → APU).

- **[АЛЬТЕРНАТИВА: SimConnect/MSFS API интеграция]** Отложено/отклонено для
  основной ветки: требует Windows-инструментария, несовместимо с текущей средой
  разработки; в будущем возможна как отдельный модуль у пользователей MSFS.
- **[АЛЬТЕРНАТИВА: WebAssembly-симулятор систем]** Явное over-engineering на
  данном этапе.

### 7.4 Поиск и навигация [ПРЕДЛОЖЕНИЕ]

- `tools/build_search_index.py` собирает JSON-индекс (title, headings, текст,
  теги, glossary) → статический файл `search_index.json`.
- Клиентский поиск (vanilla JS, простая инверсия индекса) — мгновенно, оффлайн,
  без серверных затрат. Объём контента (сотни файлов) легко помещается в память.
- **[АЛЬТЕРНАТИВА: SQLite FTS5 серверно]** Резервный вариант, если индекс
  вырастет >нескольких МБ; API не меняется (`/api/search`).
- Навигация: хлебные крошки Course → Module → Lesson, prev/next между уроками,
  боковое оглавление урока (из секций).

### 7.5 Адаптивный интерфейс [ПРЕДЛОЖЕНИЕ]

- Mobile-first: базовые стили = телефон, `@media (min-width)` — расширения
  (сейчас наоборот [ФАКТ], один max-width query — переработать инкрементально).
- Компоненты: липкая нижняя навигация на мобильных, складное оглавление,
  крупные тач-цели (важно для квизов и панелей), безопасные зоны iOS/Android.
- Сохранить существующую дизайн-систему (тёмная тема, CSS-переменные, карточки)
  как основу `style.css` [ФАКТ].

## 8. Система авиационной достоверности

Это ядро проекта. Реализуется **как данные + автоматические проверки**, а не
как свод правил, который легко забыть.

### 8.1 Четыре уровня достоверности (обязательная маркировка)

| Метка `certainty` | Значение | Визуальная маркировка |
|---|---|---|
| `real-airbus` | Реальные сведения/процедуры Airbus | Синяя плашка «REAL AIRBUS» |
| `a32nx` | Реализация FlyByWire A32NX | Зелёная плашка «A32NX» |
| `msfs` | Особенности/ограничения MSFS 2024 | Оранжевая плашка «MSFS» |
| `simplified` | Учебное упрощение | Жёлтая плашка «УПРОЩЕНО» |

Правила:
- Каждый технически значимый блок/вопрос/шаг сценария несёт `certainty`.
- Блоки `simplified` визуально **не могут** выглядеть как `real-airbus`
  (другой цвет, иконка, текст «это упрощение, не реальная процедура»).
- В каждом уроке с `certainty: simplified` присутствует автоматический дисклеймер.
- Общий баннер различий «реальный самолёт ≠ симулятор» — в base.html на всех
  страницах обучения.

### 8.2 Источники и версионирование

- Единый реестр `content/sources/sources.yaml`: id, издатель, версия/ревизия,
  дата проверки, характер доступа (открытый/ограниченный).
- Утверждение без источника → валидатор возвращает ошибку для типов
  `real-airbus`/`a32nx`/`msfs` (для `simplified` источник не обязателен,
  но желателен).
- При изменении версии источника (например, новый релиз FBW-документации) —
  поиск всех ссылок `source: <id>` и пере-ревью затронутых уроков; валидатор
  показывает список.
- `review.status`: `draft` → `in-review` → `verified`; `verified` требует
  `reviewer` и `date`. **Правило публикации:** уроки `draft` видны только с
  плашкой «черновик» (или скрыты — настраивается), не выдаются за проверенные.
- Рецензент — владелец/сводный список; запись фиксирована в YAML (Git-история
  дополняет — кто и когда менял).

### 8.3 ReviewGate [ПРЕДЛОЖЕНИЕ]

Модуль, который:
- при загрузке контента проверяет схему и правила достоверности;
- предоставляет шаблонам фильтры/данные для рендера плашек и дисклеймеров;
- питает страницу `/quality` (служебную): статусы всех уроков, устаревшие
  источники, уроки без ревью — «панель качества» контента.

### 8.4 Соответствие AVIATION_STANDARDS.md [ФАКТ]

Все 12 правил файла отображаются в механизмы:

| Правило | Механизм |
|---------|----------|
| 1–2 официальные источники | реестр sources.yaml, `kind` источника |
| 3 не выдумывать | валидатор: утверждение ⇄ источник |
| 4 маркировка 4 уровней | `certainty` + плашки |
| 5 что и почему | структура секций (обязательный блок rationale для процедур) |
| 6 взаимодействия систем | тип урока system, поля interactions |
| 7 normal/abnormal/emergency | тег `ops_mode` у секций/сценариев |
| 8 не выдавать симуляторное за реальное | запрет `certainty: simplified` в блоках процедур real-airbus (правило валидатора) |
| 9 дисклеймер лицензии | фиксированный баннер в base.html |
| 10 записывать источники | схема claims/sources |
| 11 версии документации FBW | `version`/`checked` в реестре |
| 12 непроверенное ≠ авторитетное | статусы review + плашки |

## 9. Безопасность

**[ФАКТ]** Сейчас: сервер на 127.0.0.1, без auth, без форм записи, без секретов.

**[ПРЕДЛОЖЕНИЕ] Принципы и меры:**

1. **Автентификация — не нужна** в текущей модели (локальный однопользовательский
   режим). Если позже появится публичный хостинг — только тогда вводить сессии
   (Flask-Session/cookie), CSRF-токены (Flask-WTF), rate-limit. Не раньше.
2. **Секреты:** их нет и не появится в Git; `.env` вне репозитория при необходимости;
   AGENTS.md правило 10 уже фиксирует запрет.
3. **Отладка:** `debug=True` [ФАКТ] — только на localhost; в config.py вынести
   в переменную окружения, чтобы исключить Werkzeug-debugger при возможном
   хостинге.
4. **XSS:** контент — Markdown из собственного репозитория; рендерить через
   безопасную библиотеку Markdown с отключённым сырым HTML; YAML-поля — только
   Jinja2-автоэскейп. Никаких `|safe` без ревью.
5. **Инъекции:** SQLite — только параметризованные запросы (placeholders), без
   строковой конкатенации.
6. **Загрузки файлов:** отсутствуют — нет поверхности атаки; если появятся
   (картинки от пользователя) — отдельное проектирование.
7. **CSRF:** POST-эндпоинты API (/api/progress/sync, /api/quiz/check) —
   JSON-only + SameSite cookie; достаточно для localhost.
8. **Приватность:** прогресс хранится локально; никакой телеметрии.

## 11. Масштабирование

### 11.1 По контенту (главное направление)

- Архитектура линейно масштабируется: новые уроки = новые YAML/MD файлы; ядро не меняется.
- 12 фаз ROADMAP [ФАКТ] отображаются на каталоги курсов без изменения движка.
- Ограничение: индекс контента в памяти — при тысячах уроков понадобится ленивая

- `aircraft/<profile>/` — данные; курсы ссылаются на профиль (`aircraft: fbw-a32nx`).

- Сценарии и панели систем параметризуются профилем → движок переиспользуется

- Один локальный пользователь → возможен мультuprofile (users.id уже в модели).
- Публичный хостинг — отдельное решение владельца [ФАКТ: без одобрения не
  публиковать]: тогда добавляются auth, HTTPS, реальный WSGI-сервер (waitress
  — прост, кроссплатформен). Ядро менять не придётся.

## 12. Сравнение технологических решений

### 12.1 Хранение данных

| Критерий | SQLite | PostgreSQL | JSON-файлы | MySQL/MariaDB |
|---|---|---|---|---|
| Установка в Termux proot | встроена в Python | сервер + сервис | нет | сервер + сервис |
| Транзакции | да (WAL) | да | нет | да |
| Обслуживание | файл | backup/миграции | ручное | backup/миграции |
| Аналитика прогресса | SQL | SQL | код | SQL |
| Риск для проекта | минимальный | высокий (ops) | растёт с данными | высокий |

**Решение: SQLite** (стандартный модуль `sqlite3` — ноль новых зависимостей,
[ФАКТ] уже запланирован в TECHNICAL_SPEC.md). Отклонённые альтернативы указаны выше.

### 12.2 Формат контента

| Критерий | Markdown+YAML | Чистый YAML | JSON | БД |
|---|---|---|---|---|
| Читаемость длинного текста | отличная | плохая | плохая | — |
| Структурированные метаданные | front matter | да | да | да |
| Diff-ревью в Git | отличное | хорошее | шумное | невозможно |
| Валидация схемы | нужна (pydantic/ручная) | нужна | нужна | — |
| Написание русскими авторами | удобно | муторно | муторно | инструменты |

**Решение: Markdown для текста секций + YAML front matter/отдельные YAML для
метаданных, вопросов, сценариев.** JSON отклонён как текстовый формат (нет
комментариев, шумные diff), БД отклонена для контента (теряется Git-ревью).
Разметка Markdown — минимальная, с кастомными расширениями §6.3; сырой HTML в
контенте запрещён.

### 12.3 Шаблоны

**Решение: Jinja2** (уже входит в Flask [ФАКТ]).
- **[АЛЬТЕРНАТИВА: Mako/Chameleon]** — нет преимуществ, новая зависимость.
- **[АЛЬТЕРНАТИВА: SPA-фреймворк вместо SSR]** (React/Vue): сборка Node в proot,
  потеря SEO/скорости первого рендера, разрыв с текущим кодом. Отклонено.
- **[АЛЬТЕРНАТИВА: генерация статического сайта (Pelican-стиль)]** — интересная
  опция будущего, но убивает интерактив (квизы, сценарии, прогресс). Отклонено
  как основа; возможен экспорт-модуль позже.

### 12.4 Frontend JS

**Решение: vanilla JS, модульные файлы без сборки.**
Интерактивность известна заранее: чек-листы, квизы, поиск, сценарные шаги,
панельные виджеты — всё реализуется без фреймворка. Ноль инструментов сборки
критично для Termux [ФАКТ].
- **[АЛЬТЕРНАТИВА: Vue/React через CDN]** — отклонено: потеря оффлайн-надёжности,
  зависимости от сети, сложность тестирования.
- **[АЛЬТЕРНАТИВА: Alpine.js/htmx]** — возможный лёгкий апгрейд, если vanilla
  код начнёт дублироваться; решение отложено, совместимо с текущим стеком.
- **[АЛЬТЕРНАТИВА: Web Components]** — приемлемо, но усложняет поддержку;
  обычные модули ES + шаблонные `<template>` покрывают нужды.

### 12.5 Прогресс: локально или серверно

**Решение: двухступенчато.** localStorage (M2) → SQLite (M3) с API-синхронизацией.
- **[АЛЬТЕРНАТИВА: сразу SQLite]** — требует auth-модели и CSRF раньше времени,
  тормозит перенос контента (главную ценность проекта). Отклонено.
- **[АЛЬТЕРНАТИВА: только localStorage навсегда]** — потеря данных при очистке
  браузера, нет аналитики слабых тем между устройствами. Отклонено.

### 12.6 Архитектура

**Решение: модульный монолит.** Обоснование в §3.2. Микросервисы, отдельный
поисковый сервис, отдельный сервис квизов — отклонены навсегда для этого
масштаба; границы blueprints оставляют путь к выделению, если однажды понадобится.

## 13. Поэтапный план миграции

Принципы: каждый этап оставляет приложение запускаемым [ФАКТ, требование
TECHNICAL_SPEC]; легаси-URL `/`, `/flight-training`, `/lesson/cold-and-dark`
работают на всех этапах; перед каждым этапом — Git-контрольная точка.

### M0 — Фиксация базы (без функциональных изменений)
- Перенести этот документ в репозиторий как ARCHITECTURE.md.
- `requirements-dev.txt` (pytest), `tests/test_routes.py` (3 легаси-маршрута = 200).
- **Готовность:** pytest зелёный, приложение идентично по поведению.

### M1 — Каркас приложения (рефакторинг без изменения поведения)
- `app.py` → пакет `academy/` с `create_app()`; blueprint `core` и `courses`
  с сохранёнными URL.
- `base.html`, `macros.html`; `index.html` и `flight_training.html` наследуют base
  (визуально идентично).
- Вынести inline-стили/JS урока в `lesson.css`/`lesson.js`.
- **Готовность:** все 3 URL = 200, визуальная идентичность, pytest зелёный.

### M2 — Контент как данные (первый реальный перенос)
- Создать `content/courses/flight-training/...`, перенести содержимое
  `cold_and_dark.html` в `lesson.yaml` + `sections/*.md` (порциями, с
  `certainty`-разметкой; существующий текст сохраняется).
- ContentLoader + CourseRegistry + динамический рендер процедуры.
- Прогресс чек-листа → localStorage (`a320academy.progress.v1`).
- **Готовность:** `/lesson/cold-and-dark` рендерится из данных; функционал
  чек-листа и квиза сохранён; localStorage переживает перезагрузку.

### M3 — Банк вопросов и QuizEngine
- `content/questions/`, типы single/true-false/multiple, серверная проверка,
  `quiz_block.html` + `quiz.js` (универсальные).
- Существующий вопрос Cold & Dark переносится в банк.
- **Готовность:** урок рендерит квиз из данных; проверка серверная; тесты QuizEngine.

### M4 — SQLite прогресс и повторение
- `data/academy.db`, схема §5.4, sync localStorage→БД, `/progress` (обзор,
  слабые темы EWMA).
- **Готовность:** прогресс выживает очистку localStorage; страница прогресса
  показывает статистику; миграция localStorage одноразовая и идемпотентная.

### M5 — Масштабирование контента и поиск
- Новые курсы по фазам ROADMAP (сначала aviation-fundamentals, затем aircraft-systems);
  glossary + `{{term}}`; поисковый индекс + `/api/search` + UI-поиск; страница
  `/quality` (ReviewGate-панель).
- **Готовность:** минимум 2 курса с полной иерархией; поиск находит уроки по
  EN и RU терминам; /quality не показывает verified-уроки без источников.

### M6 — Практика и сценарии
- ScenarioEngine + scenario.yaml; перенос Cold & Dark в интерактивный сценарий;
  первые панели систем (электрика) на декларативной модели.
- **Готовность:** сценарий Cold & Dark проходим пошагово от Cold & Dark до
  готовности к запуску; электрическая панель реагирует на переключатели согласно
  размеченным правилам A32NX.

### M7 — Расширение на другие самолёты
- Выделить `aircraft/` профиль полностью; проверить, что ни один курс
  fbw-a32nx-специфики не остался в общих курсах; документировать процесс
  добавления самолёта.
- **Готовность:** новый профиль добавляется копированием каталога + правкой YAML
  без изменений Python-кода.

## 14. Приоритеты и риски

### 14.1 Приоритеты

1. **P0 — достоверность** (§8): без неё проект вреден. Раньше красивого UI.
2. **P0 — контент-как-данные** (M2): разблокирует всё остальное.
3. **P1 — тесты контента** (M0/M1): защита от деградации.
4. **P1 — мобильный UX** (в каждом этапе): основной сценарий использования.
5. **P2 — SQLite, повторение, поиск**: ценность растёт с объёмом контента.
6. **P2 — панели систем/сценарии**: самая трудоёмкая часть, после устойчивой базы.
7. **P3 — мульти-самолётность**: «не мешать», а не «сделать сейчас».

### 14.2 Риски и меры

| Риск | Вероятность | Урон | Мера |
|---|---|---|---|
| Выдуманные/упрощённые процедуры выданы за реальные | среднее | критический (ядро ценности) | обязательная `certainty`+sources в валидаторе; тесты; ReviewGate |
| Разрастание объёма контента → потеря качества ревью | высокое | высокий | статусы review, `/quality`, инкрементальные курсы |
| Переписывание Cold & Dark сломает работающий урок | среднее | среднее | этап M1 идентичен визуально; легаси-тесты; Git-точки |
| Усложнение инфраструктуры (соблазн фреймворков/сервисов) | среднее | высокое (Termux) | зафиксированные решения §12; правило 11 AGENTS |
| Потеря прогресса при переходе localStorage→SQLite | низкое | среднее | идемпотентный sync, экспорт/импорт JSON |
| Источники FBW меняются между релизами | высокое | среднее | version+checked в реестре; пере-ревью по ссылкам |
| Одиночный ревьюер (владелец) — bottleneck | высокое | среднее | чек-листы ревью; `/quality` как трекер; деление на малые уроки |
| Несоответствие исходной и рабочей копий (Termux/оригинал) | среднее | высокое | [ФАКТ] правило не трогать оригинал; периодическая сверка Git |

### 14.3 Явно отложенные решения (за пределами этого проекта)

- Публичный хостинг, auth, HTTPS — только по решению владельца [ФАКТ].
- SimConnect-интеграция с MSFS.
- Генерация статического экспорта контента.
- Продвинутый SRS-алгоритм.
